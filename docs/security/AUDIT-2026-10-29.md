## Summary

The platform's security posture is still good. There are no Critical or High findings:
- Every server action re-authorizes, validates and rate-limits.
- User HTML goes through allow-list sanitizers behind a nonce CSP.
- Production dependencies are clean.

The one real issue is **business logic**: event XP can be self-farmed by any member, and it goes stale when an event or team is deleted. This undermines the leaderboard, which is a headline feature. It's safe to ship as-is. Fix M1 before promoting the leaderboard or seasons.

Fix first:
1. Recount XP when events or teams are deleted, and stop counting self-hosted events.
2. Pin the backup workflow's actions and scope its tokens.
3. Run `npm audit fix` for the dev-only undici advisories.

## Attack surface

- **Hosts:**
  - `securityexile.com`: marketing and policy pages
  - `app.securityexile.com`: the community app
  - `ctf.` and `labs.`: holding pages
  - one Worker serves all of them (`src/proxy.ts`, `src/lib/site/hosts.ts`)
  - user files are served from `files.securityexile.com` (R2)
- **Auth:** Clerk only, with the Account Portal on `accounts.securityexile.com`. `authorizedParties` is bound to the serving origin. Roles (`platform_role`, `is_organizer`) change only through reviewed `wrangler d1 execute` commands.
- **Entry points:**
  - Server Actions in `src/app/{teams,events,events/[slug]/war-room,writeups,w/[handle]/[slug],me,onboarding}/actions.ts`
  - Route handlers:
    - `POST /api/uploads`
    - `GET /dev-files/[...key]` (dev only)
    - OG image routes
  - No webhooks or cron routes.
- **Data stores:**
  - D1: users, teams, events, writeups, comments, badges, seasons, audit log
  - R2: images
  - KV, plus Workers Rate Limiting bindings, for rate limits
- **User input reaching sinks:** Markdown goes to HTML through `renderWriteup`/`renderComment` (rehype-sanitize) and DOMPurify. Images go to R2 after magic-byte sniffing and metadata stripping. Free text goes to D1 through parameterized Drizzle queries.
- **CI/ops:**
  - `ci.yml`: no secrets, `contents: read`
  - `backup.yml`: nightly; holds a Cloudflare API token and R2 keys; uploads an age-encrypted artifact to a **public** repo

## Findings

### [M1] Event XP can be self-farmed, and stays after the event or team is deleted — Medium

**Where:**
- `src/lib/events/permissions.ts:24-26`
- `src/app/events/actions.ts:180-184`, `:253-262`
- `src/app/teams/actions.ts:423`
- `src/lib/profile/queries.ts:142-143`, `:46-50`

**Evidence:**

```ts
// permissions.ts:24 — anyone may create an event
case "event.create":
  return true;
```
```ts
// queries.ts:142 — every roster entry counts, whatever the event's state or host
+ (select count(distinct er.event_id) from event_registrations er, json_each(er.roster_json) j
   where j.value = ${userId}) * ${XP_FOR.eventPlayed}
```
```ts
// events/actions.ts:180 — deleteEvent: registrations go via ON DELETE CASCADE, no recountXp
const [, deleted] = await db.batch([
  db.update(writeups).set({ spoilerUntil: null }).where(and(eq(writeups.eventId, event.id), noOthers)),
  db.delete(events).where(and(eq(events.id, event.id), noOthers)).returning({ id: events.id }),
]);
```
```ts
// teams/actions.ts:423 — last member out disbands the team; its registrations cascade, no recount
await db.delete(teams).where(eq(teams.id, team.id));
```

**Impact:** any onboarded member can farm XP alone:
1. Create a solo team. The creator is its captain, which makes them a lead.
2. Create up to 3 `ctf` events a day (`LIMITS.eventCreate`).
3. Register the team for each event and roster themselves. `setRoster` recounts immediately and awards badges.

That's +75 XP a day, so `legend` (1500 XP) takes about 20 days with no real activity.

Deleting the events afterwards is allowed: they're upcoming, and no other team has registered. That removes them from every listing, so a moderator can't even find them to hide. The stored `users.xp` still keeps the points, because no recount runs. The all-time leaderboard (`topMembers`) reads that stored value. Season boards recount live, but they also count self-hosted events.

This contradicts [docs/XP.md](../XP.md), which says XP is designed so it "can't be … farmed". There's no in-app tooling to undo it. A side effect: legitimate players on a disbanded team keep XP whose evidence is gone, and the next backfill silently removes it.

**How to confirm (local dev):**
1. Sign in, create a team, and create an event starting tomorrow.
2. Register the team, tick yourself on the roster and save. `/u/<you>` shows +25 XP.
3. Delete the event. `/u/<you>` still shows the 25 XP, and `select xp from users where handle='<you>'` agrees.
4. Run the docs/XP.md backfill. The XP drops back.

**Fix:**

(a) Recount the people who lose a registration in the same transaction, as `unregisterTeam` already does.

```ts
// deleteEvent: read rosters first
const rosters = await db.select({ roster: eventRegistrations.roster }).from(eventRegistrations).where(eq(eventRegistrations.eventId, event.id));
const players = [...new Set(rosters.flatMap((r) => r.roster))];
const [, deleted] = await db.batch([
  db.update(writeups).set({ spoilerUntil: null }).where(and(eq(writeups.eventId, event.id), noOthers)),
  db.delete(events).where(and(eq(events.id, event.id), noOthers)).returning({ id: events.id }),
  ...players.flatMap((id) => recountXp(db, id)), // runs after the cascade, so the recount sees the rows gone
]);
```

Do the same in the disband branch of `leaveTeam`: read the team's registration rosters, then `db.batch([db.delete(teams)…, ...recountXp…])`.

Caveat: if the `noOthers` guard stops the delete, the recount is a no-op, which is harmless because recounts are idempotent.

(b) Don't pay XP for playing your own event. In both `xpExpression()` and `seasonStandings()`, join `events` and add:

```sql
join events e on e.id = er.event_id
where j.value = ${userId}
  and coalesce(e.created_by, '') <> j.value
  and coalesce(e.owner_team_id, '') <> er.team_id
  and e.hidden_at is null          -- optional: also closes docs/XP.md "Known gap"
```

Update the backfill command in docs/XP.md to match, and run it once after deploying.

**Residual risk:** an alt account can host the event for the main account. That takes a second onboarded account with its own 3-a-day limit, and a moderator can see and hide the event. Requiring at least two registered teams, or an ended event, would close it further. Both need a scheduled recount, because XP is stored.

**Refs:** CWE-840 (business logic errors), OWASP A04:2021 Insecure Design.

### [L1] Backup workflow trusts mutable action tags and install scripts while holding production credentials — Low

**Where:** `.github/workflows/backup.yml:22-27`, `:36-43`, `:55`

**Evidence:**

```yaml
- uses: actions/checkout@v5
- uses: actions/setup-node@v5
- run: npm ci
# …
CLOUDFLARE_API_TOKEN: ${{ secrets.BACKUP_CLOUDFLARE_API_TOKEN }}
R2_ACCESS_KEY_ID: ${{ secrets.BACKUP_R2_ACCESS_KEY_ID }}
R2_SECRET_ACCESS_KEY: ${{ secrets.BACKUP_R2_SECRET_ACCESS_KEY }}
# …
- uses: actions/upload-artifact@v4
```

**Impact:** the job runs every dependency's lifecycle scripts (`npm ci`) and three third-party actions by mutable tag. Later steps on the same runner receive a Cloudflare API token and R2 keys. A compromised tag, or a malicious package version, could read production D1/R2 credentials:
- A bad package could be pulled in through a lockfile update that review missed.
- A bad install script could tamper with `node_modules/wrangler` before the export step runs.

Secrets are scoped to individual steps, which helps but doesn't isolate them: everything runs on the same runner.

**How to confirm:** check the token's permissions under Cloudflare dashboard → My Profile → API Tokens → `BACKUP_…`. Check the R2 key's bucket scope under R2 → Manage API tokens.

**Fix:**
- Pin the actions to full commit SHAs, keeping the version tag in a comment. Do the same in `ci.yml` (previous audit #17).
- Least privilege:
  - The Cloudflare token gets only the D1 permission `d1 export` needs, on this one account. It needs nothing for Workers, DNS or Zones.
  - The R2 key is **Object Read only**, scoped to `security-exile-uploads`.
- Optional: `npm ci --ignore-scripts`. Verify that `wrangler d1 export` still runs, since workerd and esbuild resolve their binaries through optional dependencies.

**Refs:** CWE-829, OWASP A08:2021 Software and Data Integrity Failures.

### [L3] `redirect_url` forwarded to the Account Portal unchecked — Low, needs verification

**Where:** `src/app/sign-in/[[...sign-in]]/page.tsx:11`, `src/lib/auth/urls.ts:14-17`

**Evidence:**

```ts
if (usesAccountPortal) redirect(portalUrl(SIGN_IN_URL, await searchParams));
// portalUrl copies every query param, including redirect_url, onto accounts.securityexile.com
```

**Impact:** if Clerk accepted any `redirect_url`, then `app.securityexile.com/sign-in?redirect_url=https://evil.example` would send a freshly signed-in user to a lookalike page. That's a credible phishing aid on a security community's own domain. Clerk production instances only allow redirects to the app's own domains by default, so this is most likely already safe.

**How to confirm:**
1. Open `https://app.securityexile.com/sign-in?redirect_url=https://example.org` in a private window and sign in.
2. Clerk should land on the app (or refuse), not on example.org.

**Fix (only if it does redirect):**
- Set allowed redirect origins in Clerk (`allowedRedirectOrigins`, or the dashboard's redirect allow-list) to `https://app.securityexile.com` and `https://securityexile.com`.
- Or drop `redirect_url` in `portalUrl` unless it's a same-origin path.

**Refs:** CWE-601.

## Checked — no issue found

- **Proxy and CSP** (`src/proxy.ts`): a per-request nonce with `'strict-dynamic'`, no `unsafe-inline` or `unsafe-eval` for scripts in production, `frame-ancestors 'none'`, `object-src 'none'`. `authorizedParties` is bound to the serving origin. HSTS, nosniff and XFO are in `next.config.ts`.
- **Host split** (`src/lib/site/hosts.ts:34-57`): redirect targets are fixed origins plus the request path. There's no open redirect, because `//evil` stays on the fixed host.
- **Uploads** (`src/app/api/uploads/route.ts`):
  - member-only, with an Origin check (CSRF)
  - `Content-Length` and a streamed 5 MB cap
  - magic-byte type detection
  - JPEG/PNG/WebP metadata stripping that now **fails closed**
  - an atomic per-member quota insert
  - keys built server-side from ULIDs
- **`/dev-files`:** returns 404 unless `NODE_ENV === "development"`. It also requires a strict key regex, and serves with `nosniff` and `default-src 'none'`.
- **Server actions changed since 02d1676:**
  - covered: events (`createEvent`, personal hosting, `deleteEvent`, `setRoster`), teams (`decideRequest`, `kickMember`, `transferCaptaincy`, `leaveTeam`, `redeemInvite`), writeup social (`toggleHeart`, `addComment`, `editComment`, `deleteComment`, `setCommentHidden`), writeups (`saveWriteup`, `setPublished`, `deleteWriteup`, `previewMarkdown`), and `redeemSecret`
  - each one calls `requireMember`, checks permission server-side, validates with Zod or an equivalent, and rate-limits
  - previous findings #3–#13 are confirmed fixed in the code
- **IDOR / mass assignment:** IDs are always scoped to the parent that was checked. Inserts and updates set explicit fields, never a spread of client data. `platformRole` and `is_organizer` are never written in-app.
- **XSS:**
  - The writeup and comment pipeline uses a rehype-sanitize allow-list, with raw HTML shown as text. Protocol-relative hrefs are now treated as external (`src/lib/writeups/render.ts`).
  - War-room notes use DOMPurify with an http(s)-only URI regex (`src/components/markdown/sanitize.ts:32`).
  - Event descriptions render as plain text.
  - Event and challenge URLs must be http(s) (`src/lib/events/validation.ts:27`).
  - `dangerouslySetInnerHTML` is used only on sanitized HTML and the static fx init script.
- **SQL injection:** every query uses the Drizzle builder or a `sql` template. The single `sql.raw` (`src/lib/db/schema.ts:31`) builds CHECK constraints from internal enum constants.
- **Data exposure:**
  - Profiles select an explicit public column list (`src/app/u/[handle]/page.tsx:25`).
  - Stats return aggregates only.
  - The leaderboard returns handle, display name, avatar and XP.
  - OG images judge visibility as an anonymous reader, so drafts, hidden and spoiler-locked content gets the generic card.
  - Secret badges appear only once earned.
- **Spoiler lock:** `spoilerFor` reads the event end inside the write, which closes the extend-vs-save race.
- **Secrets:**
  - No live keys in the tree or in git history; history matches are only `sk_test_…` and `sk_live_…` placeholders in docs.
  - `.env*`, `.dev.vars*`, `*.pem` and `.clerk/` are ignored.
  - `server-only` guards the DB, auth and secrets modules.
  - The untracked `debug.log` is Chrome ICU noise.
- **Backup scripts** (`scripts/backup.mjs`, `scripts/lib/wrangler.mjs`): `execFileSync` with no shell, and table identifiers are quoted. The archive is age-encrypted before upload (public-key recipient; the private key is offline). Both workflows declare `permissions: contents: read`.
- **Production dependencies:** `npm audit --omit=dev` reports 0 advisories.
- **CORS:** no CORS headers are set, so cross-origin reads are blocked by default.
